# Phase 12 — UI Design Contract

> Visual and interaction contract for Phase 12 (Flare Early-Warning).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **PLATFORM:** Native **iOS app in SwiftUI** — NOT web/CSS/React. The web-oriented template fields
> (px spacing, hex colors, shadcn/Tailwind, line-height ratios, registry) are `not applicable (native iOS)`
> or expressed in their SwiftUI equivalents. shadcn / registry-vetting gates do **not** apply.
>
> **THIS IS A REUSE PHASE — NOT A NEW DESIGN SYSTEM.** Phase 12 adds a single new **"Flare early-warning"
> section** to the EXISTING, already-checker-verified `InsightsView` dashboard, rendering a new `.flare`
> `InsightKind` through the EXISTING, kind-agnostic `InsightCardView`. **It introduces NO new tokens, NO new
> components, NO new visual language, NO new color, NO badge/alert/banner surface.** Every
> spacing/typography/color/accessibility/dismiss/confidence decision is **inherited verbatim** from the
> LOCKED Phase 8 contract (`08-UI-SPEC.md`, status: approved) — exactly as the Phase 11 Recommendations
> section did. This document declares ONLY the deltas:
>   1. the new `.flare` section (header copy + placement **FIRST** among the insight sections + omit-when-empty),
>   2. the **CALM, uncertainty-first, non-alarmist, non-diagnostic** flare copy (`FlareCopy`),
>   3. the new **alarmist/diagnostic-term scan** that gates that copy (mirrors the Phase-11 imperative scan),
>   4. the a11y identifiers for the new section/cards.
>
> **THE ONE PHASE-12-SPECIFIC DESIGN TENSION — A "WARNING" THAT MUST NOT ALARM.** This is the single design
> idea that makes Phase 12 different from Phase 11. Despite the word "warning," the flare early-warning is
> rendered with the **identical calm styling as every other insight** — the SAME neutral `InsightCardView`,
> the SAME color-independent confidence pill (text word + SF-Symbol shape, never hue). There is **NO red, NO
> alarm/warning color, NO badge, NO exclamation mark, NO `!`/`exclamationmark` glyph, NO urgent treatment,
> NO animation, NO haptic, NO banner**. The honesty posture (uncertainty-first, "something to keep an eye
> on," "not enough data yet" when insufficient, pervasive "not medical advice," non-diagnostic) is carried
> **entirely by COPY**, never by alarming visuals. A calm card placed first ≠ an alarm.
>
> **FIVE HONESTY CONSTRAINTS (four inherited from Phase 8 + one new) — they shape every flare card:**
> 1. **Confidence is plain-language ONLY** — "Low / Medium / Higher — possible association" + an SF-Symbol
>    shape. NEVER a number/percentage/coefficient (inherits D-11; D-03). No false precision.
> 2. **CALM, NON-ALARMIST, NON-DIAGNOSTIC copy** — the flare card is a discussion prompt phrased
>    uncertainty-first ("your recent pattern looks similar to times before higher-symptom days — something to
>    keep an eye on / discuss with your clinician"), NEVER a binary "you will flare," NEVER an
>    alarm/certainty/diagnostic word ("attack", "diagnose", "predict", "will flare", "warning!", "alert",
>    "emergency", "urgent"). Enforced by a NEW alarmist/diagnostic-term scan layered on the existing
>    forbidden-verb / gendered-token / numeric-confidence / imperative scans (D-04). The scan is the
>    choke-point and **wins over any template wording**.
> 3. **Color is NEVER the sole signal, and NEVER an alarm hue** — confidence carries text word + SF-Symbol
>    shape (inherited `InsightCardView` confidence pill); dismiss is gray/secondary, never red; and crucially
>    the flare card itself uses **no red / no alarm color at all** — it is the same neutral card as a trend.
> 4. **Honest absence by non-existence** — a zero-warning flare section does **NOT** render (no empty shell,
>    no placeholder, no "all clear" badge). A suppressed / sparse / insufficient / no-supported-warning user
>    sees **NO** flare section at all — never a fabricated/speculative warning (D-05 / D-07 / D-08 / SC2).
> 5. **IN-APP ONLY — NO push (SC2)** — there is no notification/alert/banner surface to design in this phase.
>    The flare warning lives ONLY as a card inside the Insights dashboard. The flare module must not touch
>    `NotificationScheduler` / `UNUserNotification` (D-06; guard-tested, mirroring `ReportNoNetworkTests`).
>    **This contract specs NO notification/push/local-alert UI of any kind.**

## Component & Interaction Inventory (the Phase-12 deltas only)

### A. The new "Flare early-warning" section (D-07)

- **Placement:** a new `Section` in `InsightsView`, added **FIRST** among the insight sections — BEFORE
  "Trends" — because the flare early-warning is the most time-sensitive / discoverable insight (D-07). Final
  section order, top → bottom (after the pinned disclaimer):
  **Flare early-warning → Trends → Cycle phase → Possible associations → Recommendations.**
  > Note: this is the one ordering nuance left to Claude's discretion in CONTEXT — resolved here as
  > **first among the insight sections, still BELOW the pinned `DisclaimerBanner`** (the not-medical-advice
  > framing must never be displaced by the warning). Being first conveys time-sensitivity by **position
  > only**; it carries the identical calm styling as every other section.
- **Built with the existing helper:** call the SAME `section(title:identifier:kind:)` builder used by the
  other four kinds, with `title: FlareCopy.sectionFlare`, `identifier: "insights.section.flare"`,
  `kind: .flare`. The helper already filters `coordinator.insights` by kind and **omits the section entirely
  when it has zero insights** — so the honest-absence behavior is inherited with no new code path.
- **Omit-when-empty (D-05 / D-07 / D-08 / SC2):** a zero-warning flare section does NOT render — no empty
  shell, no "no warning right now" placeholder, **no "all clear" reassurance badge** (an "all clear" message
  is itself a claim and is forbidden — silence is the honest absence). A suppressed / sparse / insufficient
  user, or any user without a *supported* warning, has **no `insights.section.flare` element at all**
  (provable by ABSENCE, mirroring the cycle-phase-suppressed and recommendations-absent tests). This is the
  make-or-break honesty rule: **never fabricate or speculate a flare warning.**
- **Rows:** each row is the EXISTING `InsightCardView`, unchanged, rendering a `.flare` `Insight`. Its
  `supportingData` switch already routes `.flare` to the words-only evidence line ("Seen across {n} logged
  days." + window label) — NEVER a coefficient/percentage. No chart. Typically **at most one** flare card
  (the heuristic emits a single composed warning when supported), but the section is kind-agnostic and would
  render any `.flare` cards the gate surfaces.
- **Insufficient → honest, NOT alarming:** when data/confidence is insufficient the engine either omits the
  section entirely OR (Claude's discretion, planner's choice) emits a single `isInsufficiencyNotice` `.flare`
  card that `InsightCardView`'s sparse branch renders as a calm **"not enough data yet"** state (no chart, no
  confidence pill) — **never a speculative warning** (D-05). Either way the user never sees a fabricated alarm.
- **Disclaimer / recompute / instant-load:** all inherited from §A of the Phase-8 contract (the pinned
  `DisclaimerBanner` stays at the very top ABOVE the flare section, the non-blocking "Updating…" caption,
  `loadCached()` then `dataChanged()` on appear). No new triggers. **No notification/push/local-alert surface
  is added (SC2 / D-06)** — the flare warning exists only as this in-app card.
- **A11y identifier:** `insights.section.flare` (and, provable by absence for an unsupported/insufficient
  user, the non-existence of that element).

### B. The flare card (reused `InsightCardView`, kind `.flare`)

Structure is the **inherited** fixed top→bottom layout (no change to the view):

1. **Headline** — the engine's `insight.headline`, verbatim: the **calm, uncertainty-first** line
   (e.g. *"Your recent pattern looks similar to times before higher-symptom days."*). Non-causal,
   non-diagnostic, NEVER "you will flare," NEVER an alarm word.
2. **Confidence pill** — inherited: text word ("Low / Medium / Higher — possible association") + per-level
   SF-Symbol shape. Plain-language only, no number (D-03). Reads exactly like every other card's pill — no
   special "alert" styling.
3. **Detail** — the engine's `insight.detail`, verbatim: the non-prescriptive, calming elaboration
   (e.g. *"This is a pattern in your own data, not a prediction — something to keep an eye on and discuss
   with your clinician."*). Optionally a short "what's contributing" note (Claude's discretion, D-01) phrased
   descriptively and non-causally (e.g. *"based on a recent rising pattern and a factor you've logged
   recently"*) — subject to the full copy scan.
4. **Supporting data** — words-only evidence: "Seen across {n} logged days." + the window label. No chart,
   no coefficient (inherited `.flare` branch of `supportingData`).
5. **Basis note** — "Based on your logs." (inherited `InsightsCopy.basisNote`).

- **Dismiss (D-08):** inherited verbatim — the non-destructive gray "This isn't right" affordance via
  `.swipeActions` + `.contextMenu` + the VoiceOver custom action, wired through the screen's existing
  `coordinator.dismiss(signalKey:)` → `DismissedInsight` → recompute-excludes. The flare warning is
  **dismissable** like every other insight (CONTEXT: dismissable). No new dismiss path.
- **A11y identifiers (inherited shape, new keys):** `insights.card.<signalKey>` (the flare insight's stable,
  value-independent `signalKey` — Claude's discretion per CONTEXT, must be window-independent like the
  trend/correlation/recommendation signals so dismissal survives recomputation), `.confidence`, `.evidence`,
  `.dismiss`, and (when the insufficiency notice is used) `.insufficient`.
- **VoiceOver:** inherited — the card is one contained element reading "headline, {confidence}, detail";
  dismiss is a custom action. **VoiceOver must never announce an alarm/urgency it does not see** — it reads
  the same calm plain-language summary the visible card shows.

## Copywriting Contract (the substantive Phase-12 surface)

All flare copy lives in a NEW auditable **`FlareCopy`** surface (mirroring the existing `InsightsCopy` /
`RecommendationsCopy` / `CycleSummaryCopy` posture: an `enum` of fixed strings + an `auditableStrings`
array). It is scanned by `CopyAuditTests` against `ClaimsPolicy.forbiddenVerbs` / `forbiddenGenderedTokens` /
the numeric-confidence scan / the Phase-11 forbidden-imperative scan **AND the NEW alarmist/diagnostic-term
scan** (D-04). The engine's flare `headline`/`detail` are **also** routed through `FlareCopy` templates (NOT
free text) so they pass the same scan before they are ever emitted — the audit is the honesty choke-point and
wins over any wording. (The app-side `FlareCopy.auditableStrings` and the package-internal copy mirror must
be byte-identical, guarded by a drift test, exactly as Phase 11 guards `RecommendationsCopy`.)

**Calm, uncertainty-first framing (D-03 / D-04 / D-05) — the core copy rule:** the flare warning is phrased
as something to *keep an eye on* / *discuss*, qualified up front with uncertainty, NEVER as a prediction,
diagnosis, or alarm. It always carries the not-medical-advice framing (reinforced by the pinned disclaimer).

| Element | Copy |
|---------|------|
| Section header — Flare early-warning | **"Flare early-warning"** (the new section, placed FIRST; calm, not alarmist — the word "warning" appears once in a quiet section header, never as an in-card alarm) |
| Flare headline (uncertainty-first) | A calm, non-diagnostic line, e.g. **"Your recent pattern looks similar to times before higher-symptom days."** — uncertainty-first ("looks similar to"), descriptive, non-causal, NEVER "you will flare", NEVER "{factor} will cause a flare" (avoid "higher/lower" → the "her" trap; use the existing direction wording / `Terminology` as needed) |
| Flare detail | A non-prescriptive, calming basis + invitation, e.g. **"This is a pattern in your own data, not a prediction — something to keep an eye on and discuss with your clinician."** |
| Optional "what's contributing" note (D-01, discretionary) | Descriptive + non-causal, e.g. **"Based on a recent rising pattern and a factor you've logged recently."** (NEVER "X is triggering a flare"; subject to the full scan) |
| Confidence indicator | Inherited: **"Low / Medium / Higher — possible association"** + the per-level symbol (D-03; never "certain"/"proven"/"imminent"/a percentage) |
| Insufficient state (when a notice card is shown, D-05) | **"Not enough data yet."** subtitle: **"Keep logging and this fills in over time."** (the inherited `InsightCardView` sparse state — an honest "not enough data," NEVER a speculative warning) |
| Supporting evidence line | Inherited: **"Seen across {n} logged days."** (plain words from `sampleSize`; NEVER a coefficient/percentage/p-value) |
| Window label | Inherited: **"last 7 days" / "last 30 days" / "last 90 days" / "all time"** |
| Basis note | Inherited: **"Based on your logs."** |
| Dismiss action label | Inherited: **"This isn't right"** |
| Dismiss confirmation | Inherited: gentle, inline — the card animates out (no modal, no "are you sure?") |
| Empty / suppressed / no-warning | **(none rendered)** — a zero-warning flare section is OMITTED entirely (D-05 / D-07). There is deliberately NO "all clear" / "no warning right now" copy: an "all clear" is itself a claim. Absence is shown by **non-existence**, never by a reassurance sentence or badge. |
| Push / notification copy | **(NONE — does not exist)** — there is NO push/local-notification/banner/alert surface in this phase (SC2 / D-06). No notification copy is specified because no such UI is built. |

**Copy posture rules (enforced — `ClaimsPolicy` + the NEW alarmist/diagnostic scan + the existing scans + `CopyAuditTests`):**
- **NO alarmist / urgency / diagnostic terms** (the NEW scan, D-04): forbid **"attack", "flare-up!"/"warning!"
  (as an in-copy exclamation), "alert", "alarm", "emergency", "urgent", "danger", "diagnose"/"diagnosis",
  "predict"/"prediction"/"will flare", "imminent", "certain"/"definitely", "episode"** (and obvious
  inflections) in flare copy — mind the substring trap (e.g. allow innocuous substrings; scan whole-word /
  curated like the Phase-11 imperative scan). A flare insight is a calm, uncertainty-first observation, never
  an alarm or a clinical prediction.
- **NO binary certainty** (D-03): never "you will flare" / "a flare is coming" — always qualified
  ("looks similar to," "something to keep an eye on").
- **NO imperative / directive verbs** (inherited Phase-11 scan): no "take / stop / avoid / start / should /
  must / use / try / cut" — the flare card invites discussion, it never instructs.
- **NO causal / diagnostic verbs** (inherited — engine `ForbiddenTerms` + `ClaimsPolicy`): "trigger",
  "causes", "treats", "predicts", "will", "because", "due to", "leads to". The flare warning re-frames a
  *possible association / pattern*, never a cause or diagnosis.
- **NO numeric confidence** anywhere (inherited D-11/D-03): no "%", "p =", "r =", effect-size number;
  confidence is one of three plain-language words only.
- **NO gendered tokens** (inherited): "her"/"she"/"women" — including the "higher"/"lower" substring trap.
- **NO fabricated / speculative warning** (D-05 / D-07 / SC2): a flare card appears ONLY when the `FlareEngine`
  composes real, already-gated signals that pass the single `HonestyGate` (`minSample(.flare)==21` + the
  confidence floor). A suppressed / sparse / insufficient user gets NONE — never a warning invented to fill
  space, and never an "all clear" to reassure.
- **Pervasive not-medical-advice framing** (D-04 / SC3): the pinned `DisclaimerBanner` covers the flare
  section, and the flare detail copy reinforces "not a prediction… discuss with your clinician."
- **Dismiss is a preference, not destruction** (inherited): no red, no scary confirmation, no "delete".
