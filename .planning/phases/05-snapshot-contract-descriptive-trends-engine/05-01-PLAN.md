**Enum-sourcing decision — Option D (package defines its own snapshot-facing enums), per D-18 + the phase planning guidance.** The package declares its OWN `SymptomType`/`BodyRegion`/`FlowIntensity`/`FoodTag`/`ActivityType`/`ActivityIntensity`/`SleepQuality` enums (identical `String` raw values to the app's), and the app maps app-enum → package-enum at the `daySnapshots()` boundary (Plan 03). Rationale: the 7 app enums are referenced across 17 app files; moving them (Option C) is the highest-blast-radius change in the phase and risks fragile `@_exported import`/typealias ergonomics. Option D keeps the package fully self-contained (SC1 holds by construction), leaves all 17 app files untouched, and makes the boundary map trivial because the raw values match. Drift risk (the Option-B trap) is mitigated by a Plan-03 round-trip test asserting every app-enum case maps to a package-enum case with the same raw value. The package enums carry the SAME defensive `init(raw:)` decode as the app enums (unknown raw → `.other`/`nil`), so corrupt stored data never crashes the projection.

Purpose: this is THE architectural keystone of the insights half (Phases 6/7/8/11/12 all consume `DaySnapshot`/`Insight`). Get the boundary + the contract right and generic now (D-17). Per D-01, D-02, D-03, D-04, D-09, D-10, D-18.
