**Section 1 — Stack Decisions.** A decision table (columns: Decision | Choice | Rationale | Alternatives considered), one row per decision, followed by short prose notes where a row needs nuance. Decisions to make (these are the RECOMMENDED choices — write them as decisions, not options):
- Language: Kotlin (current stable 2.x), coroutines/Flow for async. Rationale: mirrors the all-first-party philosophy of the Swift/SwiftUI iOS app.
- UI: Jetpack Compose with Material 3 as the base, themed by a ported Bloom design system (port the BloomColors token set — canvas/surface/card/ink/rose/plum/gold/petal/teal/indigo — plus typography scale and component styles into a `designsystem` package). Alternative considered: XML Views (rejected — legacy, no benefit for greenfield).
- Persistence: Room (androidx.room) with entities mirroring the 10 SwiftData models by name. Note the freedom gained vs. SwiftData+CloudKit: Room permits non-null columns and unique indices, BUT keep app-generated UUID identity columns anyway so the export format stays stable and a record's identity survives export/import round-trips. Alternatives: SQLDelight (fine, but Room is the first-party-adjacent default), DataStore (prefs only — used for consent flag and reminder settings, mirroring the iOS UserDefaults split of consent OUTSIDE the synced store).
- Health integration: Health Connect (androidx.health.connect client), READ-ONLY. Map the four iOS HealthKit reads to Health Connect record types: menstrualFlow -> MenstruationFlowRecord (+ MenstruationPeriodRecord), sleepAnalysis -> SleepSessionRecord, workouts -> ExerciseSessionRecord, dietaryEnergyConsumed -> NutritionRecord (energy field). Note the platform difference: unlike HealthKit, Health Connect DOES expose per-permission grant state — the UI may know "denied", but the product should still render denial gently (same graceful-denial UX as iOS). Availability must be runtime-gated (Health Connect is built into Android 14+, a separate installable app on older versions).
- Charts: custom Compose Canvas chart layer (recommended). Rationale: there is no first-party Compose equivalent of Swift Charts, and the app's honesty rendering rules (gap days rendered as true gaps never interpolated, absence != 0, aligned per-scale lanes never dual y-axis, count-encoded scatter with no fitted line) are bespoke logic that dominates the work regardless of library; a small owned chart layer keeps the zero-dependency privacy/maintenance posture. Alternative considered: Vico (capable Compose-native charting; acceptable fallback if Canvas layout cost balloons — record this as the explicit escape hatch). Rejected: MPAndroidChart (View-based interop, poor Compose fit).
- PDF report: android.graphics.pdf.PdfDocument + Canvas drawing (vector text/graphics, small files — the counterpart of UIGraphicsPDFRenderer). Share via FileProvider + ACTION_SEND Intent (counterpart of the system share sheet, no silent upload).
- SDK levels: minSdk 26 (the Health Connect client floor; very high device reach), targetSdk = the current Play-required level at build time. compileSdk = latest stable.
- DI: manual composition root (an `AppDependencies` mirror) — no Hilt/Koin in v1, matching the near-zero-dependency philosophy.
- Testing: JUnit + kotlin.test for the pure `:insights` JVM module (the ported EndoInsights test suite runs here as plain fast JVM tests); Room instrumentation tests for migrations; Compose UI tests for the consent gate and critical flows.
- Build: Gradle Kotlin DSL + version catalog (libs.versions.toml).
End Section 1 with a short "What NOT to use" list mirroring the iOS doc's spirit: no Firebase/any backend SDK, no analytics SDKs, no auth/accounts SDKs, no third-party charting by default, no cloud/LLM inference.

**Section 2 — Sync & Backup Strategy.** This is the biggest divergence from iOS (CloudKit has no Android client for private DBs; the no-custom-backend constraint is hard). Structure:
- RECOMMENDATION (v1): local-only storage + user-initiated encrypted export/import. Export = a versioned, platform-neutral JSON document of all user data, encrypted with a user-passphrase-derived key (AES-GCM; key derivation via a standard KDF), written/read through the Storage Access Framework (no storage permissions needed). This doubles as the GDPR portability answer and the device-migration answer. Note explicitly: the export JSON schema should be defined platform-neutrally so a future iOS exporter/importer COULD interoperate — a note, not a commitment.
- ALTERNATIVES EVALUATED (each with an honest verdict): (a) Android Auto Backup — zero code, encrypted with the device lockscreen secret on Android 9+, but opaque to the user, size-capped, Google-account-tied, and not a deliberate consent surface for special-category health data; verdict: enable for the consent flag/prefs at most, exclude the health database via backup rules, do NOT rely on it as the health-data story. (b) Google Drive appDataFolder — the closest analog to CloudKit private DB (data in the user's own Drive), but requires Google Sign-In/OAuth consent flows and Play Services coupling, which collides with the "no accounts" posture; verdict: defer, revisit as a v2 candidate if users demand multi-device.
- EXPLICIT OUT-OF-SCOPE subsection with the exact heading `### Explicitly Out of Scope: iOS-Android Cross-Device Sync` stating: the iOS app's data lives in the user's private CloudKit database which is unreachable from Android, and the no-backend constraint forbids any bridge; therefore live cross-platform sync is out of scope for the Android port entirely (one-time data handoff via the encrypted export format is the only contemplated path, and only if iOS later ships an exporter).

**Section 3 — Repository & Module Layout.** Decide: the Android app lives in an `android/` directory in THIS repo (monorepo; shared planning artifacts, shared copy-policy vocabulary, one issue tracker; the iOS XcodeGen `project.yml` and all Swift sources untouched). Show the layout as an indented directory listing inside the doc: `android/settings.gradle.kts`, `android/gradle/libs.versions.toml`, `android/insights/` (module `:insights`), `android/app/` (module `:app`). Define the two modules:
- `:insights` — pure Kotlin JVM module (kotlin("jvm") plugin, NO Android plugin), the mirror of the EndoInsights Swift package. Contains the domain value types (DaySnapshot etc.), the domain enums, and the engines: TrendsEngine, CyclePhaseMapper, CorrelationEngine (BH-FDR, Fisher exact, Mann-Whitney U, Cliff's delta), RecommendationsEngine, FlareEngine, HonestyGate, ForbiddenTerms. Boundary rule: Kotlin stdlib only — enforced by a lint test mirroring the iOS BoundaryLintTests (a source scan asserting no `android.`/`androidx.` imports in the module).
- `:app` — the Compose application. Package sketch: `data/` (Room entities + repository + consent store), `health/` (Health Connect import), `insightsbridge/` (maps Room rows -> `:insights` DaySnapshot values at the boundary, mirroring iOS `daySnapshots()`), `ui/` (screens by feature), `designsystem/` (Bloom port), `report/` (PDF).
Close the section with the dependency rule: `:app` depends on `:insights`, never the reverse.
